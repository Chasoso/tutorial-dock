# Tutorial Dock 技術設計案

状態：提案・検証前（2026-10-12）。この文書は技術判断の出発点であり、実装確定や実証済みを意味しません。正式な要求は [requirements.md](requirements.md) を参照してください。

## 1. 全体構成（候補）

Electronを第一候補とし、メインプロセスがウィンドウ・教材ファイル・表示先を管理、レンダラープロセスがガイドバーと画像ビューアのUIを担う。

```text
YAML / images (local)
      │
      ▼
Main process ── parse / validate / normalize
      ├── Guide Bar BrowserWindow (frame:false, top edge)
      ├── Slide BrowserWindow (frame:false, centered, on demand)
      ├── display selection (Electron screen)
      └── Windows AppBar bridge (native API; feasibility spike required)
```

- レンダラーでNode.js統合を無効化し、contextIsolationを有効化する。
- preload経由で必要最低限のIPCのみ公開し、教材内容を信頼しない入力として扱う。
- OS操作、ファイルダイアログ、パス検証、教材読み込み、AppBar登録はメインプロセス側に集約する。
- 外部URL・HTML・任意JavaScriptを教材から直接実行する機能はMVPに含めない。

## 2. ガイドバー

- 選択ディスプレイ上端に、枠なし・幅は当該ディスプレイ相当のガイドバーを表示する。
- 左：ステップ番号、タイトル、説明。右：教材ボタン、前／次、進捗、設定、折りたたみ。
- 通常時の高さは一定、初期目標90px。折りたたみ時30–36pxは暫定値で、UX検証で確定する。
- ボタン数が多いときは右カラムの限られた横幅に収まる分を表示し、残りは「その他」に入れる。表示順は教材定義順を維持する。
- 教材未読み込み時は「教材を開く」を提示し、ステップ操作は無効化する。
- レイアウトはDPI・文字の折り返しで破綻しないことを確認する。バーの高さを説明文に応じて自動変更しない。

## 3. Windows AppBar連携（リスク高）

AppBar API（SHAppBarMessage等）を用いて作業領域を予約する方式を第一候補とする。Electron単体のBrowserWindowオプションでは作業領域の予約は行えないため、Windowsネイティブ呼び出し手段を先行検証する。

検証対象：
- AppBar登録／位置・サイズ更新／解除のライフサイクルとWindowsメッセージ処理
- プライマリ・セカンダリディスプレイでの座標、DPIスケーリング、タスクバー共存
- 折りたたみ／展開、接続／切断、異常終了時の回復
- 最大化した通常アプリと排他的フルスクリーンの違い

予約失敗時は通常の最前面バーで継続し、UIに失敗状態を表示する。フォールバックは正常AppBar実装の代替ではない。ネイティブブリッジが難しい場合は方式を検証結果として再提案し、要求を黙って変更しない。

## 4. 表示先切り替え

起動時はプライマリへ配置。設定メニューから表示先を選ぶ。旧画面の予約を解除→新画面へ移動→新画面に予約、という遷移を扱い、失敗時に作業領域の予約状態が食い違わないようにする。ディスプレイ切断時は使用可能な画面へ移動する。

## 5. 教材データモデル案

```yaml
title: Tableau 基本操作
steps:
  - id: data-overview
    title: データの確認
    description: データペインからフィールドを確認します。
    buttons: []
  - id: bar-chart
    title: 棒グラフの作成
    description: |
      「カテゴリ」を列、
      「売上」を行へ配置します。
    buttons:
      - label: 操作方法
        action: image
        src: images/how-to.png
      - label: 完成例
        action: image
        src: images/result.png
```

暫定スキーマ案：
- ルートの `title` は表示用文字列、`steps` は1件以上の順序付き配列。
- 各ステップの `id`（教材内で一意）、`title`、`description` は必須。 `buttons` は省略可（空配列相当）。
- 各ボタンの `label`、`action` は必須。`action: image` では `src` が必須。
- 将来のアクション追加に備えて `action` を識別子とする。ただし未知のアクションは致命的エラーとして拒否する。
- 相対画像パスは選択されたYAMLの親ディレクトリを基準に解決する。許可する参照範囲やシンボリックリンクの扱いは安全性検証で確定する。
- 実装時にJSON Schema等による形式検証の採用を検討する。

## 6. 教材の読み込み・更新

- ファイル選択後、YAMLのパース→構造検証→画像ファイル存在／可読性チェック→有効な教材状態を構築→画面に適用する。
- 構文エラー・ステップ不正・ID重複・未対応アクションは致命的。読み込みを適用せず既存の正常状態を保持する。
- 画像の欠落・読み込み不能は軽微。対応ボタンを無効化し警告を表示する。
- 明示的な「再読み込み」のみ対応。現在のステップIDが残ればその位置を保持、なければ先頭へ。
- 画像を表示中は既存の画像ビューを維持し、閉じた後の再表示から更新結果を使う。画像ファイルの差し替え時のキャッシュ制御は検証事項。

## 7. 画像ウィンドウ

- 選択ディスプレイ中央に、タイトルバーなしの別ウィンドウを開く。開いたときは画像全体を縦横比を変えずに収める。
- マウスホイール、＋／−によるズーム、ドラッグでパン、倍率リセット、明示的な閉じるボタンを用意する。
- 画像を閉じてもステップと操作アプリを変更しない。初期ズーム倍率は開くたびにリセット（暫定）。
- 安全なローカル画像読み込みを採用し、教材ファイルからリモートコンテンツを読み込まない。

## 8. テスト戦略と段階的実装

1. **教材とガイドバー**：YAMLバリデーションのユニットテスト、ボタンオーバーフロー、空表示、マウス進行。
2. **画像ビューア**：ズーム・パン・リセット・閉じる、画像欠落エラー、教材切り替えと再読み込み。
3. **Windowsネイティブ連携**：AppBar領域予約・解放・折りたたみ・フォールバック。Windows実機で最大化と異常終了を検証。
4. **複数ディスプレイ**：ディスプレイ選択、切断・再接続、DPI差、スライド中央位置。
5. **配布**：インストール不要exeを作成し、Node.js未導入のWindows実機で起動。オンライン画面共有で最終確認。
